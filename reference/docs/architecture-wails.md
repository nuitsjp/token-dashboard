# Wailsアーキテクチャ

[architecture.md](architecture.md) の Wails 固有の構成を補足する文書です。プロダクト固有のシステム構成は同書、実現パターンは `design/UCP-n.md`、保存方式・データ定義は [データ設計](design/data.md) に記録し、本書への転記は行いません。

## 1. 構成と責務

Windows 専用の Wails v3 アプリとし、単一リポジトリ・単一 Go モジュールで構成します。フロントエンドは React・TypeScript・Vite、TanStack Router/Query、Mantine・CSS Modules を使用し、Router はファイルベース・ハッシュ履歴とします。

フロントエンドは利用者との対話をユースケース単位で構成し、Go は画面や対話手順に依存しない機能を提供します。ユースケースと機能は n:n で対応し、画面・フック・Service との1:1対応は要求しません。

| 配置 | 責務 |
| --- | --- |
| `main.go` | 依存関係の生成・接続、Service 登録、アプリ起動 |
| `frontend/src/app/` | Provider・Router の組み立て、アプリ全体の終了確認と診断表示 |
| `frontend/src/routes/` | ルート定義とユースケースの配置（loader による事前取得） |
| `frontend/src/usecases/<目的>/` | 対話進行、入力途中の状態、機能の組み合わせ、専用 UI |
| `frontend/src/features/<機能領域>/` | Query 定義、更新要求、変更イベント購読 |
| `frontend/src/shared/` | 特定のユースケース・機能アクセスに依存しない共用部品 |
| `internal/<機能領域>/` | 機能 Service、業務処理、永続化、外部 API・OS 操作 |

呼び出し経路は `usecases → features → 生成バインディング → Go機能Service` とし、`features` は画面・ユースケースへ依存しません。生成されたデータ型の参照は制限しません。`frontend/bindings/` は Wails CLI の自動生成成果物のため直接編集せず、Go 側の公開 API を変更した場合は生成コマンドで更新します。

対話制御はコンポーネントから始め、必要な部分をカスタムフックへ分離します。Go も機能領域内で必要な関数・型へ分け、固定の多層構造は設けません。インターフェイスは具体的な差し替えや検証上の必要性がある境界に限定し、依存はコンストラクターで渡します。

## 2. 状態と更新

| 状態 | 管理主体 |
| --- | --- |
| 業務データ・バックグラウンド処理 | Go |
| 取得結果のキャッシュ・取得や更新の実行状態 | TanStack Query |
| 遷移状態（表示対象 ID・検索条件等） | TanStack Router |
| 編集下書き・確認段階などの対話状態 | React（複数画面にまたがる場合は対話中に維持される共通親） |

Query は機能・取得条件ごとに定義し、ユースケース間で共有します。編集下書きは取得データから分離し、再取得で上書きしません。保存失敗時は維持し、完了・中止時に破棄します。

保存成功後は関連 Query の無効化・再取得を基本とし、変更イベントも同一経路へ接続して重複取得を抑えます。保存成功後の再取得失敗は、保存失敗と区別します。

## 3. 機能の契約と結果の確定

機能 Service を Wails へ直接登録し、公開メソッドと入出力型は Go 側で定義します。TypeScript 側は生成バインディングと生成型を利用します。内部型と公開型は、内部実装の都合や機密情報が露出する場合に分離します。

入力検証と成立条件の確認は Go で行います。不可分の更新は単一操作にまとめ、トランザクションを Go 内で完結させます。保存成功と変更通知は結果確定後に返します。保存先の変更と、複数保存先の同期は別の機能として扱います。

操作結果は戻り値・エラー、変更・進捗通知は Wails Events を使用します。イベントの受信履歴を正本とせず、現在の状態は取得操作で確認できるようにします。画面の終了・購読解除・処理のキャンセルは区別します。公開エラーは `code`・`message`・必要時の `fieldErrors` を保持し、Promise を reject します。Go は内部原因を公開情報と分離し、フロントエンドはコードに応じて表示と対話の再開を決めます。

## 4. モックと検証境界

仕様確認用モックは画面・対話制御・Query を本番と共用し、Vite のモジュール参照設定（`@notes-service`）で差し替えます。契約は生成型と共有し、既定は実処理とします。固定データの移動・削除とテスト作成時点は [モック標準](../../docs/standards/mock-driven-development.md) に従います。

合成点は機能領域（Go の Service）ごとに1つの参照名です。新しい機能領域 `<name>` の確認用モックを作るときは、次の4箇所を揃えます。

| 場所 | 追加内容 |
| --- | --- |
| `frontend/vite.config.ts` | `@<name>-service` の alias。`WAILS_FRONTEND_MODE=mock` のとき固定データ、それ以外は `bindings/.../internal/<name>/service.ts` |
| `frontend/tsconfig.json` | 同名の `paths` を実処理側へ向ける（型検査は常に実契約で行う） |
| `frontend/eslint.config.mjs` | `usecases/`・`shared/` からの直接 import 禁止対象に `@<name>-service` と `@bindings/**/<name>/service` を追加 |
| `frontend/tests/fixtures/<name>.ts` | 生成型を import し、`CancellablePromise` を返す同名の関数だけを持つ固定データ。業務ロジックや永続化は再実装しない |

`features/<name>/queries.ts` は `@<name>-service` からのみ Service を import します。実処理へ切り替えた後は固定データを削除または移動し、alias の分岐だけを残します。同梱の `tests/fixtures/notes.ts` はこの機構を示す試験用データです。

検証は Playwright による実処理 E2E を中心とします。シナリオの E2E は `frontend/tests/e2e/usecases/<ユースケース名>/<シナリオ名>.spec.ts` に置き、`test.step` の区切りをシナリオの条件・手順・受け入れ条件に合わせます。ブラウザ確認は Wails server build、ネイティブ操作や環境依存動作は Windows 実機で確認します。Vitest・React Testing Library・Go 標準テストは必要なリスクを補います。

## 5. 実行とデータ保護

単一インスタンス・単一ウィンドウを既定とします。リソースとバックグラウンド処理は Go の Service が所有します。終了前の未保存確認はフロントエンド、安全な停止判断は Go が担い、終了確定後に停止・解放します。

業務データ・設定・秘密情報は Go 側で管理し、アプリ配置先と分離したユーザー領域に保存します。秘密情報は通常の設定と分け、保存形式の変更は明示的な移行で扱います。読込失敗時に空データで上書き保存しません。

本番 UI は同梱アセットを使用し、外部コンテンツにアプリの権限を与えません。診断ログは Go の `slog` へ集約し、機密情報を除いて容量制限付きでローカル保存します。

## 6. 配布とアプリ内更新

Go とフロントエンドを一体ビルドし、ユーザー単位の未署名 NSIS インストーラーとして配布します（配布元は共有フォルダまたは GitHub Releases）。

Go の更新 Service が更新情報とインストーラーを取得し、更新情報の Ed25519 署名とインストーラーのハッシュを検証します。利用者の同意と未保存確認後、NSIS へ引き渡してアプリを終了します。NSIS は旧プロセスの終了を待って適用し、成功後に再起動します（更新でユーザーデータは削除されません）。更新用署名は Windows のコード署名とは別に扱い、未署名アプリの実行可否は配布先のポリシーで確認します。
