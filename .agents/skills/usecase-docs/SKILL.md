## 文書構造

連番IDを設けず名称で識別し、ユースケース名はプロジェクト内、シナリオ名は所属ユースケース内で一意にする。親は `docs/usecases/<名称>/README.md`、子はその直下の `scenarios/<名称>.md` に配置し、先頭の `# 名称` をディレクトリ名・ファイル名と一致させる。所属は配置で決まり、ID・所属項目は置かない。主アクターには利用者・外部システムのほか、バッチでは起動契機のイベントや時刻（例: 毎日 2:00、ファイル到着）を書く。この場合、目的には誰がどの結果を得るかを書き、手順のアクター列にはイベントの発生や時刻の到来を書く。

| 文書 | 必須項目 | 任意項目 |
| --- | --- | --- |
| ユースケース | `## 主アクター`、`## 目的`、`## シナリオ`（子への個別リンクのみ）、`## 実現パターン`（設計へのリンク） | `## 前提`、`## 共通の受け入れ条件`など共通事項 |
| シナリオ | `- 種別: 主成功` または `拡張`、`- UI確認: 要` または `不要`、`## 手順`（`#`・`アクター`・`システム` の表）、`## 受け入れ条件`、主成功の `## 開始条件` または拡張の `## 分岐条件` | 必要な補足 |

親の一覧は所属する全シナリオを1回ずつ参照し、主成功は1本とする。拡張の分岐条件には分岐する操作・状態と条件を記載し、変動する手順番号だけで参照しない。手順の各行には、アクターの操作とそれに対するシステムの振る舞いを書く。固有の条件・手順・期待結果は子、共通事項は親だけで管理する。未着手のユースケースはプロジェクト一覧だけに記載でき、本文とリンクは不要。

## 作成と変更

新規作成時は [ユースケース雛形](assets/usecase.md) と [シナリオ雛形](assets/scenario.md) を使用する。雛形は実仕様ではなく、構造検査の対象外。任意項目と種別に該当しない条件欄を除き、合意した内容を記入する。必須項目を空欄や `{{...}}` のままにしない。

シナリオ追加時は親の一覧へ個別リンクを追加する。改名・移動時はパスと文書・テストの参照も更新する。プロジェクトルートで `python scripts/doc_check.py .` を実行する。検査は必須項目、選択値、リンクと一覧の対応、同名の E2E がある場合は手順表と区切りの対応を確認し、仕様の妥当性・利用者の承認は判定しない。変更前後の条件・動作・期待結果も照合する。
